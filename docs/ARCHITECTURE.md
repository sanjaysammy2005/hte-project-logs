# TraceLock — Architecture

Tags: **[Paper]** from the paper · **[Rec]** our recommendation · **[Gap]** unresolved (see `PROJECT_PLAN.md` §5).

## 1. The system in plain language

Imagine a notebook where every page has a fingerprint, and each page's fingerprint also includes the previous page's fingerprint. If someone rips out, rewrites, adds or swaps a page, the fingerprints stop matching from that point on. That is the **hash chain**.

TraceLock adds two more protections:

1. **Context.** Every page also records *who* wrote it, *in which session*, *what they did just before*, *which step number this is* and *when*. The fingerprint covers all of this. A checker can therefore notice when a page is genuine but no longer fits its story, for example when a session jumps from step 1 to step 3, or a user opens a file without having authenticated. These are the **provenance checks**.
2. **Batch summaries.** Every group of pages (a batch) gets one summary fingerprint called a **Merkle root**. A whole batch can be checked with one comparison, and a single page can be proven to belong to a batch using only a few fingerprints.

Later, a **verifier** re-reads everything, recomputes every fingerprint, re-checks every context rule and rebuilds every batch summary. It answers **Valid** or **Tampering Detected**, and in the second case says where and why. **[Paper §IV, §VI-E]**

The limits matter just as much. TraceLock *detects* changes; it cannot *prevent* them. Someone who can rewrite **all** the pages and **all** the fingerprints consistently will not be caught. See `SECURITY_LIMITATIONS.md`. **[Paper §IX-B]**

## 2. End-to-end flow

```
 Application / workload generator / TraceLock's own login
            │  POST event (actor, session, type, payload)
            ▼
 ┌────────────────────────────────────────────┐
 │ 1. Event Capture Layer           [Paper V-A]│  validate input (Pydantic)
 ├────────────────────────────────────────────┤
 │ 2. Context Enrichment Layer      [Paper V-B]│  server adds: session_seq,
 │                                             │  prev_event_type, timestamp
 ├────────────────────────────────────────────┤
 │ 3. Integrity Layer               [Paper V-C]│  canonical bytes → SHA-256
 │                                             │  H_n = SHA256(E‖C‖H_{n-1})
 ├────────────────────────────────────────────┤
 │ 4. Merkle Batch & Storage Layer  [Paper V-D]│  PostgreSQL; seal batch →
 │                                             │  Merkle root stored
 ├────────────────────────────────────────────┤
 │ 5. Provenance Verification &     [Paper V-E]│  recompute chain + 5 checks
 │    Response Layer                           │  + Merkle roots → report
 └────────────────────────────────────────────┘
            │
            ▼
   React dashboard: VALID / TAMPERING DETECTED (batch, first record, check)
```

**[Paper]** five layers and ten pipeline steps (§IV, §V, Fig. 1).
**[Rec]** steps 1–3 and the hash-chain append happen inside **one database transaction under a per-stream lock**. This guarantees that two concurrent events never claim the same predecessor.

**[Gap → Q13]** The paper extends an existing prototype that is not in this repo. **[Rec]** TraceLock is standalone. Events arrive through an authenticated ingestion API, so an external application (including the paper's prototype) can send events later. TraceLock's own operator logins and logouts are also logged as real events in a `system` stream.

## 3. Key concept: streams

**[Rec]** Each **log stream** is an independent chain with its own genesis, chain indices and batches. Stream kinds:

| Kind | Purpose | Lab may mutate? |
|---|---|---|
| `primary` | Real events (e.g. TraceLock's own `system` stream, events from an external app) | **Never** |
| `synthetic` | Generated by the seeded workload generator | No (cloned first) |
| `lab` | Clone of another stream; tampering is applied here | Yes |

Streams keep tampering experiments isolated from genuine data, as CLAUDE.md requires. They also let us label demonstration data clearly.

The paper describes a single log, so streams are an implementation convenience. Within one stream the paper's design is followed exactly.

```
                          experiments, schemas

                          0004 experiment runs
  config/transitions.v1.json
  experiments/            smoke.json, full.json
  scripts/demo_walkthrough.py
  tests/  unit/ (pure: crypto, provenance, engine, metrics, config, security)
          api/  (DB-backed: auth, events, concurrency, verification, lab, experiments, CLI)

```

**Design rule [Rec]:** `crypto/` and `provenance/` are pure functions over plain data. They do not import the database or FastAPI. This means:
- They can be unit-tested exhaustively without Docker.
- The verifier uses exactly the same code that ingestion used to compute the hashes.
- They are short and easy to explain during a presentation.

## 8. Data flow for a single event (detailed)

1. The client sends `POST /api/v1/streams/{id}/events` with `{actor_user_id, session_id?, event_type, payload}`.
2. Pydantic validates the input. It checks that `event_type` is a known type and that the payload holds only strings, integers, booleans and null. Unicode is normalised to NFC.
3. The service opens a transaction and takes `pg_advisory_xact_lock(stream_id)`.
4. It reads the chain head (the last `chain_index` and its `entry_hash`, or the genesis value for an empty stream).
5. If there is a session, it reads that session's latest event to get `prev_event_type` and the previous `session_seq`, and applies the ingestion policy (Q6).
6. It assigns `event_timestamp` (server UTC, microseconds) and `session_seq = previous + 1`.
7. It builds the canonical bytes and computes `entry_hash`.
8. It INSERTs the record and commits. The lock is released.
9. If the unsealed record count has reached the batch size, the service seals a batch (a separate short transaction).

## 9. Verification flow (summary)

The full algorithm is in `VERIFICATION.md` §6. In short, the verifier:
1. reads all records of a stream in `chain_index` order;
2. checks index continuity, the previous-hash links and the recomputed hashes;
3. replays session state and applies the five provenance checks plus timestamp order;
4. rebuilds every sealed batch's Merkle root and checks its leaf count;
5. produces a report and stores it as a verification run.
